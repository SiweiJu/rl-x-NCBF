## 1. F6 confirmed (state on `pncbf-v2` = `multistep` @ 1ed8736)

- Old `cpo/flax_full_jit/cpo.py` = clipped PPO (ratio clip 0.1, 10 epochs, minibatches) on the advantage
  `(A_r - λ A_c) / (1 + λ)` with λ ← clip(λ + 0.05 (J_c − d), 0, 100). No FVP, CG, trust region or line search.
- `ppo_lagrangian.flax_full_jit.PPOLagrangian(CPO)` only overrode `general_properties`; default configs were
  identical → the two baselines were the **same algorithm**. `cost_limit = 0.0` in both.
- **Cost**: `env_state.info["constraint/cost"]` (fallback `terminated`). In the locomotion MJX env
  (`mjx/environment.py:1470-1518`): `constraint_terminated` (below-height / body-tilt termination, plus obstacle
  collision when obstacles are on) × `safe_time_shortfall`; with the default `safe_time_limit_seconds = 0` the
  shortfall is 1, so **cost = 1 on the failure step, 0 otherwise** (≤ 1 per episode). qvel-limit terminations
  are terminations but not costs.
- **J_c** in the old code = mean over envs of the summed cost of one 128-step rollout (not per episode).
- **Cost critic**: same MLP as the value critic (512-LN-256-128), regression to cost-GAE returns
  (`cost_gamma = 0.99`, `cost_gae_lambda = 0.9`), own Adam; cost advantages standardized per minibatch.
- **Logging**: `constraint/{mean_step_cost, mean_rollout_cost, cost_limit, cost_violation, lambda, safe_time,
  below_height_rate}`, `eval/constraint_cost` (= episode cost of the deterministic eval rollout).

## 3. CPO

Followed OmniSafe `omnisafe/algorithms/on_policy/second_order/cpo.py` (`_update_actor`, `_determine_case`,
`_step_direction`, `_cpo_search_step`), `omnisafe/utils/math.py` (CG) and `NaturalPG._fvp` (re-read from GitHub
main on 2026-10-22). Per update: rollout → reward/cost GAE → reward advantages standardized, cost advantages
centered only (OmniSafe buffer) → one CPO step on the full batch → reward and cost critics by MSE regression
(`nr_epochs` × minibatches, Adam, same lr schedule as PPO).

CPO step: g = ∇E[ratio A_r], b = ∇E[ratio A_c], FVP = jvp of ∇ mean KL(π_old‖π_θ) + damping·v,
x = CG(F, g), p = CG(F, b), cases 0–4 as OmniSafe (4: b≈0 & feasible → TRPO; 3: whole trust region feasible →
TRPO; 2/1: analytic dual (λ*, ν*); 0: recovery step −√(2δ/s) p that only reduces cost), backtracking line search
(decay 0.8) accepting the first step with KL ≤ δ, cost-surrogate increase ≤ max(−c, 0) and (cases 2–4) reward
improvement ≥ 0; no accepted step → no update.

Defaults: `target_kl 0.01, cg_iterations 15, cg_damping 0.1, line_search_steps 15, line_search_decay 0.8,
fvp_sample_freq 1` (OmniSafe; note OmniSafe's `_update_actor` actually passes `total_steps=20` to the line
search), `cost_measure episode`, `cost_limit 0`.

**Deviations from OmniSafe, with reasons:**
1. **Sign of r.** OmniSafe uses `r = grads·p` with `grads` the reward-*ascent* gradient, together with the
   paper's ν* = (λ*c − r)₊/s and f_a(λ) = … − rc/s. These formulas are only correct with Achiam's reference-code
   convention r = bᵀH⁻¹(−g) (his code works with the loss gradient). Checked numerically: against SLSQP on
   random trust-region QPs, the OmniSafe sign gave a wrong step in 192/222 cases (and left the trust region, e.g.
   ½xᵀHx = 0.019 for δ = 0.01); with r = −gᵀH⁻¹b all match. We use r = −gᵀF⁻¹b
   (`test_cpo_dual_matches_numerical_qp`). The line search would usually catch the KL violation, but the
   direction itself is wrong.
2. **Constraint normalization** (`cost_violation_normalization`): OmniSafe uses c = EpCost − d in episode units
   with a per-step surrogate E[ratio A_c]. By the performance-difference lemma ΔJ_c(episode) ≈ T·ΔE_t[ratio A_c],
   so the default here is **per_step**: c = (J_c − d)/T, T = mean episode length estimated from the same rollout
   (= mean step cost − d/T). `none` reproduces OmniSafe. With d = 0 and OmniSafe's normalization, any failure
   makes B < 0 → case 0 (pure recovery) at every update, so the policy would never learn to walk.
3. CG uses a guarded division instead of `+1e-6` in the denominators (our gradients are ~1e-3, where 1e-6
   biases the solution); non-finite trial steps are rejected and shrunk.
4. Critic lr/epochs/minibatches as the repo's PPO (paper scale), not OmniSafe's (lr 1e-3, batch 128) — keeps
   the comparison with PPO about the policy update only.

## 4. Tests

`JAX_PLATFORMS=cpu python -m pytest tests/test_constrained_baselines.py -q` → **17 passed** (~3 min; the
end-to-end Go2 runs are 1.5 min of that).

- λ increases while violated and decays to 0 when satisfied: gradient, PID (default gains), PID (large gains).
- PID recursion equals a python port of rlpyt/OmniSafe `PIDLagrangian`.
- episode / rollout cost measures.
- CG solves a random 30×30 SPD system.
- FVP equals the explicit Gaussian Fisher E[J_μᵀΣ⁻¹J_μ] + 2J_logσᵀJ_logσ on a tiny policy.
- CPO step: measured KL ≤ δ for c ∈ {−1, −1e−3, 0, 1e−3} and equals the logged KL.
- Infeasible constructed case (c = 10): optim_case 0, B < 0, λ* = 0, cost surrogate decreases, step ∥ −F⁻¹b.
- All five cases are selected for constructed (g, b, c); case-1/2 steps satisfy the linearized constraint and the
  trust region; analytic dual = numerical QP solution.
- End-to-end, Go2 locomotion, 16 envs, 2 updates: PPO-Lag gradient, PPO-Lag PID (episode measure, d = 0.01),
  CPO (d = 0.01): all logged metrics finite.

## 7. T08 results follow-up (2026-10-23)

### 7.1 λ dynamics: no bug, the constraint was never satisfied in training

T08 used `cost_measure = episode` for all methods (`run_baseline.sh`), gradient lr `cost_lambda_lr = 0.05`,
PID gains as in §2. `constraint/measured_cost` (= Σcost / #finished episodes per rollout, i.e. failures per
episode of the *stochastic training* policy) is the value compared with d. Histories (wandb `P0_T08_baselines`,
7524 updates each):

| Run | λ at 10/25/50/75/90 % / final | mean J_c over updates 30–100 % | share of updates with J_c > d (30–100 %) |
|---|---|---|---|
| gradient d=0 | 5.1 / 14.3 / 21.8 / 27.4 / 30.1 / 31.7 | 0.060 | 1.00 |
| gradient d=0.01 | 4.9 / 15.0 / 22.5 / 27.5 / 29.3 / 30.4 | 0.061 | 0.99 |
| gradient d=0.05 | 5.0 / 11.1 / 13.6 / 13.8 / 13.5 / 13.1 (max 13.9 at 62 %) | 0.054 | 0.51 |
| PID d=0 | 1.6 / 3.2 / 4.8 / 6.1 / 6.8 / 7.3 | 0.069 | 1.00 |
| PID d=0.01 | 1.6 / 3.3 / 5.0 / 6.0 / 6.5 / 6.8 | 0.070 | 1.00 |
| PID d=0.05 | 1.4 / 2.7 / 3.5 / 3.6 / 3.7 / 3.65 | 0.063 | 0.67 |
| CPO d=0 / 0.01 / 0.05 | — (optim case 1 in 99–100 % of updates, every step accepted) | 0.20 / 0.22 / 0.24 | 1.00 |

- The "≈ 4e-5" figure is `constraint/episode_cost` (and `constraint/mean_step_cost`, `constraint/terminated`):
  env info averaged over all steps × envs, i.e. a **per-step** failure rate. Converted:
  4e-5 × 131072 steps / 138 finished episodes = 0.038 ≈ `measured_cost` 0.036 failures per episode (gradient
  d=0.01, last update). So J_c ≈ 0.04–0.07 per episode stays above d = 0 and d = 0.01, and λ keeps rising, as it
  should. At d = 0.05 J_c ≈ d and λ plateaus (gradient: max 13.9, then slowly decreasing; PID: flat at 3.6).
- Why so slow to come down: with the gradient rule λ moves by 0.05·(J_c − d) per update. Violations are up to
  0.95 (J_c ≈ 1 early), slack is at most d, so λ decays at ≤ 0.05·d per update (≤ 5e-4 at d = 0.01): ~60k
  updates to undo λ = 30, while the run has 7.5k. This is inherent to the rule and the units, not a bug.
- Why eval shows ≈ 0 failures: eval uses the deterministic mean action (policy std ≈ 0.05–0.1 at the end) and
  one fresh 1000-step episode per env; training J_c includes the exploration noise.
- CPO: J_c ≈ 0.2 failures per episode, 3–4× PPO-Lag; with J_c > d it is always in case 1 (dual step mixing
  reward and cost). With the per-step normalization c ≈ 0.2/770 ≈ 2.6e-4, the cost term is weak relative to the
  reward term; a candidate tuning knob for T08 tuning (`cost_violation_normalization=none` is the OmniSafe
  behavior and would push it to recovery steps).
- No code change. If the asymmetry matters for tuning, the PID rule (smaller λ, same J_c) or a larger
  `cost_lambda_lr` are the levers, both within the §6.5 budget.
